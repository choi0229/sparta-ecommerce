# ADR-002: user_address_history 이력 보존 기간 정책

- 상태: 수락 (Accepted)
- 결정일: 2026-05-19
- 적용 범위: address-api `user_address_history` 테이블

---

## 배경

address-api는 주소 생성/변경/삭제가 발생할 때마다 `user_address_history` 테이블에 변경 전·후 값을 append-only로 저장한다.

```
user_address_history
  id, address_id, user_id
  action_type (CREATE / UPDATE / DELETE)
  before_recipient_name, before_recipient_address, before_is_default
  after_recipient_name,  after_recipient_address,  after_is_default
  created_at
```

이 이력은 두 가지 성격을 동시에 갖는다.

1. **운영/CS 추적 목적**: 배송지 변경 경위 조회, 고객 문의 응대, 이상 변경 감사
2. **개인정보 성격**: 수취인 이름·주소는 개인식별 가능 정보(PII)에 해당한다. 무기한 보존은 불필요한 개인정보 축적이 될 수 있다.

현재 운영 API:
- 사용자: `GET /addresses/{id}/histories?userId=` — 본인 이력만 조회
- 관리자: `GET /admin/addresses/histories` — 전체 이력, X-Admin-Api-Key 인증

테이블에는 별도 TTL, 삭제 배치, 아카이빙 로직이 구현되어 있지 않다. 데이터는 현재 무기한 누적 중이다.

---

## 선택지

### A안: 무기한 보존

이력을 삭제하지 않고 계속 유지한다. 추가 구현 없음.

- 장점: 구현 복잡도 없음. 오래된 분쟁·감사 케이스에도 대응 가능
- 단점: PII 무기한 보존. 데이터 무한 증가. 개인정보 법적 리스크 누적

---

### B안: N개월 이후 자동 삭제

주기적 배치 잡이 `created_at < now() - interval 'N months'` 조건으로 행을 물리 삭제한다.

- 장점: PII 보존 기간 제어. 테이블 크기 통제
- 단점:
  - **비가역적**: 삭제된 이력은 복구 불가. 삭제 전 검토 없이 자동 실행됨
  - 보존 기간 N 결정이 비즈니스/법적 기준 없이 임의적으로 설정될 수 있음
  - 배치 실패 시 누적 방치, 배치 성공 시 과도한 삭제 위험
  - 삭제 기준에서 제외해야 하는 케이스(진행 중 분쟁, 미확인 문의 등) 구분 로직 필요

---

### C안: N개월 이후 아카이브 테이블로 이동

`user_address_history_archive` 테이블을 만들고, 일정 기간 경과 시 메인 테이블에서 아카이브 테이블로 이동한다.

- 장점: 메인 테이블 크기 통제. 이력 비가역적 삭제 없음. 감사 시 아카이브에서 복원 가능
- 단점:
  - 아카이브 테이블 추가 (Flyway migration)
  - 이동 배치 구현 + 트랜잭션 설계 (이동 중 일관성 보장)
  - 조회 API가 아카이브까지 검색할지 여부 결정 필요
  - 아카이브 자체를 언제 삭제할지 정책이 다시 필요해짐 → 문제 이전
  - A안, B안보다 운영 복잡도가 가장 높음

---

### D안: 현재는 무기한 보존, 운영 정책 확정 전 삭제/이동 미구현

현재는 A안(무기한 보존) 상태를 유지하되, 아래 기준 중 하나를 충족하면 B안 또는 C안으로 전환한다.

- 장점: 현 시점 구현 없이 정책만 문서화. 데이터 손실 위험 없음. 정책 기준이 생기면 그때 최소 구현 가능
- 단점: 단기적으로 PII 계속 누적. 기준점 도달 후 전환 비용 발생

---

## 선택지 비교

| 기준 | A (무기한) | B (자동 삭제) | C (아카이빙) | D (정책 보류) |
|------|-----------|-------------|------------|-------------|
| 개인정보 관리 | 나쁨 | 좋음 | 보통 | 현 단계 허용 |
| 운영/CS 추적성 | 완전 | 보존 기간 내만 | 아카이브 포함 시 완전 | 완전 (현재) |
| 구현 복잡도 | 없음 | 보통 (배치) | 높음 (배치+스키마) | 없음 |
| 데이터 증가 | 무한 증가 | 통제됨 | 메인 테이블만 통제 | 무한 증가 |
| 복구 가능성 | 완전 | **없음** | 아카이브에서 가능 | 완전 |
| 정책 기준 필요 | 없음 | **보존 기간 N 결정 필요** | N + 아카이브 정책 필요 | 추후 결정 |

---

## 현재 결정: D안 채택

다음 이유로 **현 시점에서는 삭제/아카이빙을 구현하지 않는다.**

1. **보존 기간 N의 근거가 없다.**
   비즈니스 요구사항(예: "소비자 분쟁 처리는 최대 X개월"), 법적 기준(개인정보 보호법 보존 기간 산정), 운영 SLA가 아직 정의되지 않았다. 근거 없이 N을 설정하면 이후 조정이 불가피하고, 그 사이 삭제가 발생하면 복구할 수 없다.

2. **자동 삭제는 비가역적이다.**
   배치가 한 번 실행되면 삭제된 행은 돌아오지 않는다. 운영 정책 검토 없이 자동화하는 것은 위험하다.

3. **현재 데이터 규모가 삭제 배치를 요구하는 수준이 아니다.**
   `user_address_history`는 사용자가 직접 주소를 변경/삭제할 때만 행이 쌓인다. 주문마다 생성되는 이벤트 로그가 아니다. 현재 규모에서 테이블 크기가 시스템 문제를 일으킬 가능성이 낮다.

4. **관리자 조회 API가 이미 구현되어 있다.**
   `GET /admin/addresses/histories`에 날짜 범위 필터가 있으므로, 수동으로 오래된 이력을 조회·검토할 수 있다. 배치 자동 삭제 없이도 운영자가 상황을 파악하는 데 지장이 없다.

5. **C안(아카이빙)은 운영 복잡도 대비 현재 얻는 이익이 없다.**
   아카이브 테이블은 "메인 테이블 크기 통제"가 목적인데, 현재 그 필요성이 없다. 아카이브 자체의 삭제 정책도 다시 결정해야 하므로 문제를 한 단계 미루는 것에 가깝다.

## 후속 구현 기준

아래 조건 중 하나라도 충족되면 B안 또는 C안으로 ADR을 개정한다.

| 조건 | 권장 전환 방향 |
|------|-------------|
| 개인정보 보호 법적 요구사항 또는 내부 정책으로 보존 기간 N이 확정됨 | B안 (자동 삭제) |
| `user_address_history` 행 수가 10만 건을 초과하거나 조회 성능 저하 발생 | C안 (아카이빙) 또는 B안 |
| CS/감사 목적상 최근 N개월 이전 이력 조회가 필요 없다는 운영 합의 도출 | B안 (자동 삭제) |
| 데이터 주체 삭제 요청(Right to Erasure) 대응 프로세스가 도입됨 | B안 + 요청 기반 삭제 API 추가 |

---

## 현재 채택한 보완 조치

삭제/아카이빙 미구현 대신, 현재 상태에서 할 수 있는 최소 통제를 유지한다.

- `GET /admin/addresses/histories?from=&to=` — 날짜 범위 기반 조회로 오래된 이력 수동 파악 가능
- `X-Admin-Api-Key` 접근 통제 — 관리자 이력 조회 API 무단 접근 차단
- 이 ADR 문서화 — 정책 결정 시점과 근거를 남겨 향후 전환 시 참조 가능
