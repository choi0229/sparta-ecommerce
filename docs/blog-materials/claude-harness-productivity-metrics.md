# Claude Code 하네스 개발 생산성 지표

작성 기준: 2026-05-10
대상: sparta-ecommerce MSA 프로젝트

---

## 이 문서의 범위

이 문서는 **개발 생산성** 지표를 다룹니다.
서비스 런타임 성능(latency, throughput, DB connection 사용률 등)과는 별개입니다.

| 측정 대상 | 설명 | 문서 |
|---|---|---|
| 개발 생산성 (이 문서) | 하네스 도입 전후 작업 효율 변화 | 이 문서 |
| 서비스 런타임 성능 | API 응답 시간, DB 부하, Kafka lag 등 | `.claude/rules/performance-observability.md`, Grafana 대시보드 |

두 관점을 혼동하면, 하네스가 "더 빠른 코드를 만들었는가"를 측정하려는 오류가 생깁니다.
하네스는 코드 실행 성능이 아니라 **코드를 만드는 과정**에 영향을 줍니다.

---

## 왜 측정하는가

Claude Code 하네스를 구성하는 데 시간과 노력이 필요합니다.
CLAUDE.md, rules, skills, agents, guardrails, CI gate를 갖추는 데는 초기 비용이 있습니다.
"하네스가 있으면 더 빠르다"는 느낌만으로는 다음 단계 투자를 결정하기 어렵습니다.

측정의 목적은 두 가지입니다.
1. 하네스 투자가 실제 작업 흐름에 영향을 주었는지 확인
2. 어떤 요소가 가장 효과적이었는지 파악하여 다음 우선순위 결정

## 측정 지표

### 주요 지표

| 지표 | 정의 | 측정 방법 |
|---|---|---|
| 작업 완료 시간 | 요구사항 확정 시점 ~ 검증 완료 시점까지 경과 시간 | 세션 시작/종료 기록, git 커밋 타임스탬프 |
| 재작업 횟수 | 동일 작업 범위를 다시 수행한 횟수 | `docs/claude-feedback-log.md` 기록, git 커밋 이력 |
| 변경 범위 이탈 수 | 요청하지 않은 파일/로직이 변경된 횟수 | git diff 검토 기록 |
| 검증 실패 횟수 | 코드 생성 후 빌드/테스트/배포/smoke 검증에서 실패한 횟수 | CI 결과, smoke script 결과 |

### 보조 지표

| 지표 | 정의 | 주의 |
|---|---|---|
| 토큰 사용량 | Claude Code 세션당 입/출력 토큰 수 | 작업 복잡도 차이를 통제하기 어려워 단독 비교는 의미가 낮음 |

토큰 수는 "하네스 overhead가 얼마나 되는가"를 가늠하는 참고 지표로만 사용합니다.
토큰이 줄었다고 생산성이 높아진 것이 아니고, 늘었다고 나빠진 것도 아닙니다.
rules 파일 로드로 인한 컨텍스트 토큰 증가는 일관된 지침 제공의 비용입니다.

## Before / After 비교 구조

비교는 세 시점을 기준으로 합니다.

| 시점 | 설명 |
|---|---|
| **Before** | Phase 1 — 하네스 없이 Claude Code 기본 사용 |
| **After 1** | Phase 2 — CLAUDE.md + rules + skills + agents + guardrails + CI gate 도입 |
| **After 2** | Phase 3 — Karpathy 스타일 CLAUDE.md 정비 + smoke script 자동화 |

---

### 작업 완료 시간

**Before**: 측정 기록 없음.

**After 1 vs Before (정성적 관찰)**
- 세션 시작 전 프로젝트 규칙을 반복 설명하는 시간이 줄었습니다.
  CLAUDE.md와 rules 파일이 자동 로드되어, 매 세션마다 도메인 경계·Outbox 원칙·트랜잭션 규칙을 재설명하지 않아도 되었습니다.
- 하네스 구성 자체에 초기 투자 시간이 필요했습니다. 이 비용은 측정에 포함되어야 합니다.

**After 2 vs After 1 (정성적 관찰)**
- 하네스 구성 추가 비용이 줄었습니다. Phase 3는 기존 구조를 정비하는 작업이었고, 새 파일 작성보다 기존 파일 조정 위주였습니다.
- smoke script 자동화로 검증 단계에서 소요되는 수동 curl 반복 작업이 줄었습니다.

수치 비교: 측정 기록 없음.

---

### 재작업 횟수

**Before**: 측정 기록 없음.

**After 1 (관찰 가능한 데이터)**
- Phase 2에서 logistics-api 생성 후 코드 리뷰를 통한 수정이 2회 필요했습니다.
  - `OutboxPublisherJob` self-invocation 수정 (feedback-log 항목 1)
  - `@Transactional` 누락 재발 수정 (feedback-log 항목 2)
- 이 수정들은 하네스의 code-reviewer agent가 발견한 구조적 문제입니다.
- 하네스가 없었다면 발견 시점이 배포 후로 늦춰졌을 가능성이 있습니다. 단, 이 주장은 가정이며 정량화되지 않습니다.

**After 2 (관찰 가능한 데이터)**
- AddressServiceClient 작업에서 구현 완료 후 재작업은 없었습니다.
- mock address-api 검증 과정에서 이미지 미반영으로 인한 재검증이 1회 필요했습니다 (feedback-log 항목 12 참조).
  이는 하네스 자체의 문제가 아니라 배포 절차 검증 항목 누락이었습니다.

---

### 변경 범위 이탈 수

**After 1 (관찰 가능한 데이터)**
- logistics-api 생성 전 과정에서 기존 서비스(order-api, product-api, inventory-api) 파일이 변경되지 않았습니다.
- CLAUDE.md Surgical Changes 원칙 + `.claude/settings.json` deny 규칙이 함께 작동했습니다.

**After 2 (관찰 가능한 데이터)**
- AddressServiceClient 작업에서 order-api 기존 흐름에 최소 변경만 이루어졌습니다.
- mock address-api 작업에서 신규 파일 추가에 그쳤고 기존 서비스 파일이 변경되지 않았습니다.

Before와의 비교: 측정 기록 없음.

---

### 검증 실패 횟수

**After 1 (기록 가능한 데이터)**
- CI 테스트: Phase 2 완료 기준 0회 실패 (빌드/테스트 통과)
- Minikube 배포 검증: 이미지 이슈 1회 (openjdk deprecated → eclipse-temurin 교체, feedback-log 항목 해당)
- guardrails CI 오탐: 2회 (README.md, docs 파일 오탐 → 제외 패턴 수정)

**After 2 (기록 가능한 데이터)**
- CI 테스트: 0회 실패
- smoke 검증: 이미지 미반영으로 인한 재검증 1회 (feedback-log 항목 12 참조)

## 로그 수집 방식

현재 생산성 데이터는 다음 세 곳에서 수집합니다.

| 소스 | 내용 | 비고 |
|---|---|---|
| `docs/claude-feedback-log.md` | 발견된 문제, 수정 내용, 재발 방지 기록 | 수동 작성 |
| git 커밋 이력 | 단계별 타임스탬프, 변경 파일 목록 | 자동 기록 |
| smoke script 결과 | 배포 검증 pass/fail | 실행 시 터미널 출력, 자동 보존 안 됨 |

세션 수준의 데이터(프롬프트 왕복 횟수, 토큰 수, 수정 반복 횟수)는 체계적으로 기록되고 있지 않습니다.

## 결과 해석 원칙

**1. 정성적 관찰과 정량 측정을 구분한다**

"줄었습니다", "개선되었습니다"는 정성적 관찰입니다.
숫자가 없는 개선 주장에는 "(정성적 관찰)"을 명시합니다.
"XX% 빠르다"처럼 수치를 수반하는 주장은 측정 방법과 조건을 함께 기록합니다.

**2. Before 데이터가 없으면 비교가 아니라 관찰이다**

Phase 1 작업 기록이 체계적으로 수집되지 않았습니다.
Before/After 비교는 기억 기반 정성 평가입니다. 이를 "개선 수치"로 표현하지 않습니다.

**3. 하네스 구성 비용도 포함한다**

CLAUDE.md, rules, skills, agents 파일 작성에 든 시간도 총 작업 시간에 포함해야 공정한 비교가 됩니다.
초기 투자 비용을 무시하면 하네스 효과를 과대평가할 수 있습니다.

**4. 단일 프로젝트, 단일 개발자 데이터임을 인식한다**

통제 그룹 없는 before/after 비교이므로, 하네스 효과와 프로젝트 진행에 따른 자연스러운 학습 효과를 분리하기 어렵습니다.

**5. 토큰 수는 단독으로 해석하지 않는다**

rules 파일이 많아지면 컨텍스트 로드 토큰이 늘어납니다.
토큰 증가 자체가 문제가 아니라, 그 토큰이 유효한 지침을 제공하는지가 중요합니다.

## 한계

| 한계 | 내용 |
|---|---|
| Before 데이터 부재 | Phase 1 작업 기록이 체계적으로 수집되지 않음. Before/After 비교는 기억 기반 정성 평가 |
| 단일 프로젝트 편향 | logistics-api 및 address service 작업에만 적용된 결과. 다른 유형 작업에서도 같은 경향인지 불확인 |
| 측정 도구 미구성 | 작업 시간, 왕복 횟수, 수정 횟수를 자동 수집하는 도구 없음 |
| 복잡도 미통제 | Before/After 비교 작업의 복잡도가 다름. 단순한 작업과 복잡한 작업을 같은 기준으로 비교하면 오류 발생 |

## 향후 보완

| 항목 | 방법 |

| 작업 시간 측정 | 세션 시작/종료 시각을 feedback-log.md에 함께 기록 |
