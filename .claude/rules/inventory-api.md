# inventory-api 작업 규칙

`inventory-api`는 재고 수량, 재고 예약, 예약 만료, 재고 해제, 보상 처리를 담당합니다.

## 핵심 원칙

- `inventory-api`는 재고 도메인의 Source of Truth입니다.
- 재고 변경은 직접 차감보다 예약과 확정/해제 흐름을 통해 처리합니다.
- 동시 주문, 중복 이벤트, 결제 실패, timeout 상황에서도 재고 정합성을 유지해야 합니다.
- 재고가 음수가 되는 구조를 만들지 않습니다.

---

## 재고 예약 / 해제 규칙

주문 생성 시 재고는 즉시 최종 차감하기보다 예약 상태로 관리합니다.

재고 예약 시 다음을 보장합니다.

- 가용 재고 확인
- 동일 주문 또는 동일 이벤트의 중복 예약 방지
- 동시 요청 상황에서 일관성 유지
- 재고 음수 방지

결제 실패, 결제 timeout, 주문 취소, Saga 실패 상황에서는 예약 재고를 해제해야 합니다.

재고 해제는 중복 실행되어도 안전해야 하며, 이미 해제된 예약을 다시 해제해도 재고가 중복 복원되지 않아야 합니다.

존재하지 않는 예약 해제 요청도 안전하게 처리합니다.

---

## TTL 기반 예약 만료 규칙

예약된 재고는 결제 지연 또는 실패 상황에 대비해 TTL 기반으로 해제될 수 있어야 합니다.

예약 만료 처리 시 다음을 지킵니다.

- 이미 확정된 예약은 만료 처리하지 않습니다.
- 이미 해제된 예약은 중복 복원하지 않습니다.
- 예약 만료 처리는 멱등해야 합니다.
- 만료 처리 결과는 추적 가능해야 합니다.
- 주문 또는 결제 상태와의 정합성을 고려합니다.

---

## 동시성 / 멱등성 규칙

재고 로직은 높은 동시 요청 상황에서도 안전해야 합니다.

다음 상황을 고려합니다.

- 동일 SKU에 대한 동시 주문
- 동일 예약 이벤트의 중복 수신
- 결제 성공과 예약 만료의 경합
- 결제 실패와 주문 취소의 중복 처리
- 재고 부족 상황
- 재고 복원 중복 실행

필요한 경우 DB 락, 낙관적 락, 조건부 업데이트, 유니크 제약 등을 고려합니다.

Kafka 이벤트는 중복 전달될 수 있으므로 Inventory Consumer는 멱등하게 동작해야 합니다.

중복 처리는 다음 기준을 고려합니다.

- eventId
- orderId
- reservationId
- skuId
- processed event record

중복 이벤트가 중복 예약, 중복 해제, 중복 복원으로 이어지지 않도록 합니다.

---

## 트랜잭션 규칙

재고 수량 변경과 예약 상태 변경은 가능한 한 짧은 트랜잭션 안에서 처리합니다.

`@Transactional` 내부에서 오래 걸리는 외부 호출을 수행하지 않습니다.

재고 변경 중 외부 시스템 응답을 기다리는 구조를 만들지 않습니다.

이벤트 발행이 필요한 경우 Transactional Outbox 패턴을 고려합니다.

---

## 테스트 규칙

`inventory-api`의 비즈니스 로직을 수정한 경우 다음 테스트를 고려합니다.

- 정상 재고 예약
- 재고 부족으로 인한 예약 실패
- 중복 예약 이벤트
- 정상 재고 해제
- 중복 해제 이벤트
- TTL 기반 예약 만료
- 결제 성공과 예약 만료 경합
- 동시 주문 요청
- 재고 음수 방지
- 보상 처리 멱등성

테스트는 가능한 경우 다음 명령어로 실행합니다.

```bash
cd inventory-api
./gradlew test
```

테스트를 실행하지 못했다면, 실행하지 못한 이유와 사용자가 실행해야 할 명령어를 명확히 설명합니다.
